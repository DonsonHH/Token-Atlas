# 本机计时性能复查

审查的是原生日志计时快照 `5f3cb56` 到修订快照 `4f392a1`。早期 [功能 Review](native-request-timing-review.md) 的通过结果不代表资源行为已验证。

## 现场证据与原因

- 暂无活动连接时，原桌面 `3000` 次进程（Next 开发模式）仍消耗约 6.92 个逻辑核，私有内存约 756 MiB，短采样中有 23 个线程持续活动。这说明不能只把 CPU 归给 JavaScript 计时解析；未做原生堆栈采样，不宣称定位到 Next 的特定内部缺陷。
- 上轮三个预览实例处于空闲，仍合计占约 324 MiB 私有内存。已逐一停止这些预览，并停止已核实的旧 Token Atlas 开发监听器。未停止其他应用。
- 另证实计时代码本身有独立的资源问题：正常日期筛选仍在每四秒预热旧历史；首个大文件绕过批次限制，压缩大小也不等于解包大小；长期保留已解析样本并在每次请求重新克隆、分组和排序。旧的小文件测试没有覆盖这些风险。不能从上述进程采样反推出整机曾如何耗尽内存。

## Standards

3 项 P2 均关闭：单文件读入／解码不受批次约束、发现不受限且发生在共享工作前、样本保留与重复聚合不断增长。修订把约束放到了目录枚举、流解码及缓存本身；大型明文仅读头部与有限尾段，而不是从零重读；有界候选与样本分别上限 128 份和每份 256 条。最新 32 条采用有界队列，刷新服务限为一个扫描工作项，短期缓存按精确范围复用。

## Spec

2 项 P1 均关闭：第一个文件可超过额度、普通显示驱动高频全历史驻留。后续发现的摘要刷新期间可能启动定时计时、文档仍承诺补齐历史两项也已修正。桌面入口只启动一个生产服务，前台约 60 秒轮询，主用量读取期间不启动计时；归档超额显示部分覆盖，可按需缩小日期。不会用计时样本替代 token 或费用。

## 最终验证

| 证据 | 观察 |
| --- | --- |
| 旧桌面进程，空闲采样 | 6.92 核 / 756 MiB 私有内存 |
| 新桌面进程，启动后空闲短采样 | 0 核 / 95.5 MiB 私有内存 |
| 新版三轮近期请求读取，跨过缓存有效期 | 6 次实际读取约 161–413 ms，采样最高 164.8 MiB；同范围追加读取同一结果。Codex、DSH 均有速度和首字，保留部分覆盖标记 |
| 本轮读取完成后空闲短采样 | 0 核 / 141.6 MiB 私有内存 |

`pnpm verify` 通过，包括 85 项测试与生产构建。合成用例覆盖带巨行的 18 MiB 明文尾部、压缩膨胀、范围过滤、容量上限与并发合并。部署追踪没有纳入用户日志。重复运行桌面启动器不创建额外实例。最终仅 `127.0.0.1:3000` 监听；`3001–3003` 均已释放。原 DSH 用量及 Opus 5.5 参考价验证正常。数值是当前机器本次采样结果，不是所有历史规模或机器的上限。

## Node 22 压缩兼容复查

Node 22.23.5 的原生 Zstandard 解码器在一次写入收到多个帧时，可能只消耗第一个帧。常规 DSH 用量恢复使用已兼容多帧的解码路径；有读取预算的计时扫描则按解码器报告的已消费字节续读后续帧，不放宽压缩输入、解码输出或窗口限制。新增用例覆盖跨帧的同一行，以及没有解码输出的跳过帧在到达截止时间后停止。Windows 本机使用 Node 22.23.5 重新运行完整测试集，90 项均通过。
